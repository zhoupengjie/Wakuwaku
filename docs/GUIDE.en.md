## Install

### 1. Get the pet

- **One exe (Windows)**: `wakuwaku.exe` is about 11 MB (3 of them the default pet), runs from any folder and keeps her settings and pets in a `wakuwaku-data` folder beside it; to remove her, delete the two. It uses the WebView2 that comes with Windows 11, nothing else to install.

Download `wakuwaku-<version>-windows-x64.exe` from [Releases](https://github.com/zhoupengjie/Wakuwaku/releases) (in China, the same file is on [Gitee](https://gitee.com/zhoupengjie/Wakuwaku/releases)); there is nothing to install. The exe is not code-signed, so on first run Windows SmartScreen may stop it: click More info → Run anyway. Or build it yourself, see below.
- **From source**: see below.

On first launch she downloads the default pet, Claude小姐 (online; offline, the settings open by themselves so you can pick one later). For another, click the island to open the settings and pick one on the Pets page (the gallery comes straight from codex-pets.net; click Download), or paste a pet page URL.

### 2. Connect Claude Code (the plugin is recommended)

In Claude Code, enter (the settings' Agents page has copy buttons, in Claude Code's row opened):

```
/plugin marketplace add zhoupengjie/wakuwaku
/plugin install wakuwaku@wakuwaku
```

Claude Code installs and removes the plugin itself, and **we don't touch your settings file** (Claude Code notes it in its own `enabledPlugins` and takes it out on uninstall). A plugin can't start the pet, so turn on Start at login on the General page. Start at login is a Run entry in the registry; it also adds a Task Scheduler task triggered at logon, whichever her home is (`Wakuwaku at logon-<your SID>`), which starts her right after you log on instead of waiting in line behind the Run entries. With her home the taskbar, she takes it over only once Explorer has finished starting (its taskbar and desktop up, 30 s run); until then Windows' own taskbar is there. If you rename or move the exe, her next start points both at where it is now (one you turned off stays off).

If you'd rather not use a plugin, Connect in Claude Code's row of the Agents page (or Install under "Straight into settings.json" in the row opened) writes the hooks into `~/.claude/settings.json` (backed up first; removing takes out only our entries). In return, new sessions start the pet. With both on, the row turns amber with Repair, which takes our entries out of settings.json and keeps the plugin.

### 3. Connect Codex (optional)

Click Connect in Codex's row of the Agents page. It writes `~/.codex/hooks.json` (backed up first; removing takes out only our entries). Then **enter `/hooks` in Codex and trust Wakuwaku's hooks**: Codex runs only hooks you trusted. She reads Codex's own record of what it trusts (only reads it, never changes it), and the Agents page reminds you until that record trusts these hooks as they are now; once they are trusted, restarting her doesn't bring the reminder back. If the app moves, click Repair and trust them again.

How it differs from Claude Code:

| | Claude Code | Codex |
| --- | --- | --- |
| Working, waiting, done, review | ✓ | ✓ (a turn that ran `apply_patch` ends in review) |
| Errors | ✓ | No (Codex sends no event when a request fails; she goes back to idle after 15 minutes) |
| A jump when a to-do item is done | ✓ | No |
| Answer on the panel | Allow / Always allow / Deny, questions, plans | Allow / Deny |
| New sessions start the pet | With the settings.json way | Yes |

Codex hooks can only be commands: `wakuwaku.exe --wakuwaku-codex-hook` runs once and hands the event to her. On Windows Codex runs hooks in PowerShell, about 0.3 s to start each time, so Codex waits for it only when a turn ends, on a prompt, and when a session starts and ends (Codex runs no turn-end hook in the background); a turn starting and each step are reported in the background. Background hooks need Codex 0.148 or later; an older one gets only the essential hooks (waiting on a turn starting and on an edit too), and the bubble doesn't name each tool.

The pets in Codex's desktop app (`~/.codex/pets`) use the same format, so they show up on the Pets page, marked From Codex.

### 4. Connect Antigravity (optional)

Google's Antigravity is supported: the `agy` CLI and the Antigravity 2.0 desktop app. Click Connect in Antigravity's row of the Agents page. It adds a block named `wakuwaku` to `~/.gemini/config/hooks.json` (backed up first; removing takes out only that block, other tools' hooks stay). Then open a new agy session (or restart Antigravity 2.0). The standalone Antigravity IDE runs no hooks for now, so it can't be connected.

Tool approvals can be answered on the Dynamic Island (allow, always allow, deny; "always allow" is synced back to `config.json` and `settings.json`, and timeout or dismissal defers to Antigravity's native dialog). Questions stay in Antigravity.

Antigravity hooks can only be commands, run by `cmd` without reading quotes: if the app's path has a space, its 8.3 short path is written instead; with no short path either (some drives have short names turned off), installing fails, and moving the app to a folder with no spaces in its path fixes it. agy waits for the hook at each step, about 0.1–0.2 s.

### 5. Connect OpenCode (optional)

[OpenCode](https://opencode.ai/) 2.0 or later is supported. Click Connect in OpenCode's row of the Agents page: it puts a `wakuwaku.js` in OpenCode's plugin folder (`~/.config/opencode/plugins/`; with `OPENCODE_CONFIG_DIR` or `XDG_CONFIG_HOME` set, wherever OpenCode itself looks; Remove deletes it). OpenCode loads it by itself, even while it runs; nothing to restart.

She follows its turns starting, working, using tools, finishing and failing, shows the last reply, and Today counts its turns; when OpenCode asks for your approval, the panel can allow, always allow or deny, while OpenCode asks in its own window too, and the first answer counts. Sub-agents' sessions aren't shown on their own; what they ask for comes under their main session. Clicking a session goes to the terminal OpenCode runs in (with several OpenCodes open it may pick the wrong one).

How it differs from Claude Code: OpenCode runs its sessions in a background service, and the plugin there sends their events straight to her port, with no program of hers run; so OpenCode doesn't wake her (turn on Start at login), and with her not running the plugin does nothing and OpenCode asks as usual. Today's tokens don't count OpenCode's yet.

### 6. Connect oh-my-pi (omp, optional)

[oh-my-pi](https://github.com/can1357/oh-my-pi) (the `omp` command line, 18.11 or later) is supported. omp has no hooks, only extensions: click Connect in omp's row of the Agents page, and an extension of our own goes into omp's agent folder, `~/.omp/agent/extensions/wakuwaku.ts` (where `PI_CODING_AGENT_DIR` points, if set; with `omp --profile`, each profile's `~/.omp/profiles/<name>/agent/extensions/` gets one too), her port and the app's path written in it; none of omp's settings change, and Remove deletes it. Every omp started after that loads it (one already open has to be restarted).

How it differs from Claude Code:

- She follows a session starting, working and each tool it uses, finishing (the start of its reply), failing and exiting; a subagent's are left out, only the main session shows.
- omp runs in yolo by default and asks for no tool approvals; set to `always-ask` or `write`, when omp wants a tool approved she shows "Approve it in the terminal: …", and the approval is given in omp (omp has no way for an extension to answer it).
- omp's plan reviews (plan mode) can be approved or turned down on her panel, whichever of it and the terminal's review answers first.
- The extension runs inside omp's own process: each event is sent and let go, and omp never waits on her; with her not running, omp works as ever. When she isn't running and you didn't quit her (her menu's Quit, or `POST /quit`), a new omp session starts her. Clicking the session goes to the terminal window omp runs in.

### 7. Connect ZCode (optional)

Z.ai's [ZCode](https://zcode.z.ai/) is supported: the desktop app (tried with 3.15) and its CLI. Click Connect in ZCode's row of the Agents page. It adds one hook of ours to each of its 7 events under `hooks.events` in `~/.zcode/cli/config.json` and turns `hooks.enabled` on (backed up first; removing takes out only our entries and puts `hooks.enabled` back as it was). **New tasks** connect from then on; tasks already open don't. ZCode's settings list these hooks and can turn each off; the Agents page says so when one is.

Nearly as with Claude Code: starting, working, each step's tool, finishing (with its last words), edits, and Today counts it. When ZCode needs your approval, the island asks **Allow** / **Deny** (ZCode suggests no rules, so no "always"); ZCode shows its own dialog at the same time, and **whichever you answer first counts**: answered on the island, ZCode's dialog closes; answered in ZCode, the panel goes once that step is done (after a deny, once the turn ends). Handle in ZCode hands it back and brings its window to the front. With her not running, ZCode just shows its own dialog.

ZCode's hooks can only be commands, none over HTTP: each event runs `wakuwaku.exe --wakuwaku-zcode-hook <event>` once (started directly with its arguments, no shell, so a space in the path is fine), which hands it to her. ZCode waits for it at each step, about 0.1 s; the approval one may wait up to 10 minutes (the panel's own wait is shorter, and hands it back to ZCode when it runs out). A new task starts her when she isn't running (unless you quit her: her menu's Quit, or `POST /quit`).

### 8. Connect DeepSeek Harness (optional)

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (DSH) is supported: the desktop app (tried with 0.2.0-rc.2 and 0.2.1-rc.2) and the `dsh` CLI. DSH has no hooks file of its own, everything is a plugin; she brings a small plugin of her own (`integrations/dsh/wakuwaku.js`, no npm packages, nothing downloaded). Click Connect in DeepSeek Harness's row of the Agents page: she writes the plugin into DSH's folder, `~/.dsh/wakuwaku/`, and inserts it by its path in `~/.dsh/cordis.patch.yml` (`./wakuwaku/wakuwaku.js`; a layer every profile applies, the desktop app's own too; backed up first, and removing takes out only our lines, which sit between `# wakuwaku begin` and `# wakuwaku end`). Inserted by its path, it never goes into a profile's `node_modules`, so DSH's plugin manager running pnpm can't take it away. A running DSH usually loads it at once (it watches that file), no restart needed; after the plugin is updated, restart DSH.

The plugin runs inside DSH's own process and POSTs its events straight to her port: no program is started, and DSH never waits on her (2 s at most an event, nothing sent while she isn't there). After Connect, the Agents page says truthfully whether the plugin is loaded: when and in which profile once it is; "loads as DeepSeek Harness starts" while DSH isn't running; "restart DeepSeek Harness" when DSH was already running before and hasn't loaded it; and an amber "DSH plugin not working", with the reason and Repair, when DSH has been up a while without loading it. Up to 0.3.2 she used DSH's Claude Code hook bridge (`@deepseek-ai/dsh-hooks-claude-code`), which DSH no longer carries from 0.2.1, so no event ever came (zhoupengjie/Wakuwaku#61): updated to this version, she puts the plugin in its place as she starts (the file backed up beside it); where the bridge's packages are still there and it works, it stays as it is.

The DeepSeek Harness row, opened, also lets you pick DSH's "Official hook bridge" as its Way: with DSH's own Node and pnpm she installs `@deepseek-ai/dsh-hooks-claude-code` and `@deepseek-ai/dsh-hook-protocol` at DSH's version into each profile (from the registry pnpm is set to: it needs the network, a few seconds to a minute or two; when that can't be reached, "Try again from npmmirror"; should it fail, the profile is put back as it was and the plugin stays). Each of the bridge's events has DSH run her program in PowerShell, about 1 s, at a few points only: no tool of each step, and no approvals or questions answered on the island. Switching back to the plugin takes the two packages, and what installing them changed, away again. Switch either way at any time; a running DSH takes the change at once, no restart.

What works: sessions starting, working, each step's tool and finishing (an edit makes it "edited"), with DSH's own session name, its last words, the files changed and the to-do list on the island; its approvals and questions come to the panel to answer there (see [Answer Claude on the pet](#answer-claude-on-the-pet) below), DSH asking in its own window at the same time, the first answer counting; a turn you stop in DSH goes back to idle, one that fails shows the error; Today counts its turns, time and the approvals given on the island; a click on its session goes to DSH's window. A subagent DSH starts (its subagent tool, or a plugin's, like dsh-mnemon's idle review) gets no line of its own, and its task never names a session: the files it changes count toward the turn of the session that started it, while that one is at work; with that one at rest, nothing shows. What doesn't:

- No "always allow": DSH's approvals are one-shot only.
- With her out of sight (do not disturb, an app full screen) no panel comes: the island only shows "Approve in DeepSeek Harness: …", answered in DSH. A panel whose time runs out (the wait set in the settings), or handed back with Handle in DeepSeek Harness, goes back to DSH, and the session's line then says "Approve in DeepSeek Harness: …" ("Answer in DeepSeek Harness: …" for a question); DSH's own window can answer all along. With her not running, DSH goes on as it always did.
- Once the plugin is updated to the version that answers approvals, restart DSH for it (the Agents page says so).
- A new session doesn't start her: the plugin only sends her events, it starts no program.

### 9. Connect Reasonix (optional)

[Reasonix](https://github.com/esengine/DeepSeek-Reasonix) is supported: the Reasonix Studio desktop app and the command line (the Go 1.x and 2.x; tried with Studio 2.44). Click Connect in Reasonix's row of the Agents page: one hook of ours goes into each of 10 events under `hooks` in Reasonix's global `settings.json` (`%APPDATA%\reasonix\settings.json` on Windows, or under `REASONIX_HOME` when that is set; backed up first, and removing takes out only ours). If you only had the older `~/.reasonix/settings.json`, your hooks there are copied over too, since Reasonix stops reading the old file once the new one exists; removing takes the new file away again, as it was. Then **a new session in Studio, or the command line started again** (or `/reload`), is connected; sessions already open aren't.

What works: sessions starting, working, each step's tool, finishing (with its last words), edited, and errors (Reasonix's own words for them); Today counts its turns and time (and Today's tokens in 2.x); the tools its subagents, planner and guardian call count toward the session that started them, with no line of their own; a click on a session goes back to Studio's window, or the terminal or VS Code the command line runs in. What doesn't:

- **Approvals are still answered in Reasonix**: hooks in settings.json can watch them but not answer them (only a Claude Code-style hook in a plugin package can). When it waits for your approval, the island says "Approve in Reasonix: …"; when it asks you a question, "has a question for you".
- Stopping a turn in Studio shows a note in the conversation that a Wakuwaku hook "could not run · context canceled": Reasonix runs that step's hooks only after the cancel, when they can no longer start. Nothing else is affected.

Reasonix's hooks can only be commands: each event runs `"wakuwaku.exe" --wakuwaku-reasonix-hook <event>` once through `cmd.exe`, which hands it to her and prints nothing (Reasonix would pass `SessionStart`'s output to the model). Reasonix waits for it at each step, about 0.1 s; with her not running it leaves at once and Reasonix carries on. A new session starts her when she isn't running (unless you quit her). The Node Reasonix 0.x isn't supported: its hooks have only 4 events and no session id; the Agents page shows its version and leaves its settings alone.

### From source

Needs Rust (the MSVC toolchain on Windows). Only tested on Windows 11 so far; Tauri builds on macOS and Linux too, but full-screen detection, start at login, notifications and the button state are written for Windows only.

```bash
git clone https://github.com/zhoupengjie/wakuwaku.git
cd wakuwaku/src-tauri
cargo run                 # debug
cargo build --release     # target/release/wakuwaku.exe, one file
```

No Node and no Tauri CLI needed. The first run downloads the default pet; connect Claude Code (and the others) from the settings' Agents page, or, on the first open, from the welcome card at the top of General. Run from source, her settings, downloaded pets and log live in the project's `data/` folder (not in git).

## Use

- **Drag** her anywhere; she runs the way you drag, and remembers the spot.
- **Click** her: she jumps, and the window of the session she shows comes to the front. **Double-click**: out on the desktop, she flies back home.
- **A session takes you to its window**: click a session in the open island, a row on the Now page of the settings, or Handle in terminal on a prompt, and the window it runs in comes to the front: Windows Terminal, a console window, VS Code, or the Claude desktop app (which opens that very session). An app hidden in the tray (Codex's desktop app, say) is brought back out first. When the session's process has ended, the island says it can't find its window. Windows Terminal comes to the front as a window, not at the tab.
- **Mail**: on the Mail page of the settings, as in Thunderbird: give the address and password, and the incoming and outgoing servers are looked up (or type in the server, port and security). Advanced settings fold out below, as in Thunderbird's manual setup: for either server the hostname, port, connection security, authentication method and user name, with Re-test to see what the server takes without signing in. TU Dresden mailboxes (tu-dresden.de, mailbox.tu-dresden.de) are built in: the address and the ZIH password will do. Once it signs in, new mail pops up in the island with who it is from and what about, and the unread count shows otherwise (the island marks nothing read). Mail is kept on this computer as Thunderbird keeps it: all headers, and the last year of whole letters offline (or 90 days, all, or only those opened; the Mail page says how much room it takes; the first time takes a while, the account's line shows how far), so the Mail page and a letter open with no wait for the server, and new mail, deleted mail and mail read elsewhere come in by themselves; the inbox shows conversations, letters back and forth as one card that folds out into smaller cards indented as they answer one another, your own replies (from Sent) among them. The Mail page is in two panes by default, as in Thunderbird: the inbox on the left, the letter read or written on the right (↑ ↓ for the one before or after), or in one pane if you like. The inbox, with several mailboxes, all of them as one by default, or any one (each with its unread count); all letters, the unread or the starred; a star on any letter. Click a letter to read it; right-click one (or open it and press Hand to…) to hand it to the AI picked on the Mail page: the answer shows under the letter as it is written, with a box below to ask more ("write the reply"), the island says when it answered and a click there brings the letter back; the talk is kept for next time. A terminal session is in the right-click menu too. Hand letters to, on the Mail page, is one choice for every mailbox and every letter: Claude Code, Codex or Antigravity (through its command line, agy: with only the Antigravity desktop app it is there greyed, with a line saying agy is wanted and how to install it, and once agy is installed it can be picked within seconds, no restart; agy is found on the PATH, under an npm prefix of your own, scoop or winget), with its model and effort (an Antigravity model carries its effort in its name). It only reads: Claude runs no commands and has no web, Codex sits in its read-only sandbox; Antigravity has no read-only mode and asks before it changes anything, which in the talk under a letter nobody approves, so there it only reads, but for what you always allow in Antigravity. What a letter asks for, the agent tells you; it does not do it. You write letters there too: Write above the inbox, Reply on a letter, Reply all and Forward (its attachments with it) in ⋯ or the right-click menu; with files, Cc and Bcc, Ctrl+Enter to send; a letter sent is kept in Sent, and one replied to shows ↩. A reply an agent wrote in the talk becomes yours with Reply with this, to change and send; it never sends anything itself. A letter half written stays, to go on with from the top of the inbox. To reach Gmail and the like from China, the Mail page's Proxy follows the General page's Network proxy by default (itself Windows' proxy unless set: the one Clash or v2rayN set as the system proxy), or follows Windows' proxy, or takes one typed in (HTTP or SOCKS5), or none; a mailbox may have its own in its Advanced settings (Gmail through the proxy, QQ and 163 straight, say). Receiving, sending and the server lookup all go through it, SOCKS5 leaving the names for the proxy to look up; an error says whether the proxy could not be reached or the proxy could not reach the server. QQ, 163 and Gmail take an authorization code or app password (once the servers are found, the form says where to make one). For Gmail the form walks you through it in three steps: turn on 2-Step Verification (no phone number needed; an authenticator app will do), make an app password, paste it back; anything that isn't a 16-letter app password is stopped before she signs in. When signing in fails, she says which way: an app password needed, the password wrong or no longer valid, Google wanting you to confirm in the browser first, too many connections, IMAP turned off, or the network or proxy. "Sign in with Google" isn't there for Gmail yet: reading and sending Gmail through a browser sign-in takes one of Google's restricted permissions, and a published app has to pass Google's app review for it first; until then the sign-in page warns that the app is unverified, and only 100 users ever can use it. Wakuwaku is a one-person project with no need of that review, so it's an app password, and the form says so. Outlook and Hotmail take only a browser sign-in, not supported yet. The password is kept in Windows Credential Manager.
- **Plugins in the island**: while no session needs you, plugins take turns in the island, like "Today 12 turns · 1:43 · 5 approved", or the weather, or a stock; sessions always come first. Hover to see them all, scroll to turn to the next, click one to show it and open its settings. Built in: Today (turns, how long the AI worked, in seconds under a minute, and approvals given on her; a day of Antigravity sessions with no approvals given on her shows "—" for them) and Today's tokens (Claude Code's, Codex's, Antigravity's, omp's, DeepSeek Harness's and Reasonix's), on by default; and the Monitor, off: CPU, memory, network and battery, each with a switch, shown in the island as icons and numbers, updated every 1 to 10 seconds (2 by default), the CPU read from the same counter as Task Manager's, so the two agree. The monitor's settings let you pick more readings by their hardware, from one of two sources (until you pick one: LibreHardwareMonitor while it is running, else built in). Built in reads what Windows itself tells any program, with no administrator's rights and nothing installed: the CPU's actual speed; the graphics card's temperature, load, core clock and memory (and its fan, where it reports one); each drive's temperature (NVMe; orange from the drive's own warning temperature), active time and read and write rates; and in the settings alone an NVMe drive's health (life used, spare, hours on). By default it shows the CPU, memory and the network's up and down alone; anything else once picked. Windows' public interfaces give no CPU temperature or power, but the built-in source has an optional switch, "CPU temperature and power", that reads them (through namazso's signed PawnIO driver — LHM and FanControl use it too — and a small, **read-only** helper that runs as administrator; one UAC prompt to set up; with no PawnIO, the switch downloads and installs its official one, driver and modules both hash-checked; turning it off is one more UAC prompt and removes the helper but keeps the PawnIO driver; a virtual machine may not expose the CPU temperature registers). For more, or instead, switch to LibreHardwareMonitor, and with [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) running and its Remote Web Server on, pick its sensors (the CPU's and the graphics card's temperature and load, power, fans and more; the CPU's temperature and the discrete card's temperature and load by default). Without it, click Download LibreHardwareMonitor in the settings: she downloads its latest release from GitHub (the build that needs no .NET installed, checked against the SHA-256 GitHub gives), then, as administrator (Windows asks you once: allow Wakuwaku), puts it in `C:\Program Files\LibreHardwareMonitor`: it runs as administrator and may start with Windows, so it lives in a folder only administrators can change; turns its web server on in its config (on her port, in the tray once started), and starts it (the first time it starts it asks itself whether to install its driver, PawnIO). By default LHM's own task, LibreHardwareMonitor, starts it with Windows too, so no question comes each time (LHM's Options → Run On Windows Startup turns it off as well). Installed with its web server off and not running, she turns it on in its config and starts it; running, she says how to turn it on in LHM. LHM is a program of its own (open source, under the MPL-2.0); what runs as administrator is LHM itself, and the one step of hers that installs it, changes its config, makes or removes its task, or removes it (her exe with `--wakuwaku-lhm`; Windows asks each time). To remove it: right-click it in the tray → Exit, then click Remove LibreHardwareMonitor in the settings (its folder and its task go); or turn off Start with Windows yourself and delete that folder as administrator. An LHM you put somewhere yourself she leaves alone, and says where it is. Nothing is downloaded unless you click. Each source keeps its own picks, and either's readings show as icons and numbers like the rest. She can also run some for you: weather, stocks/rates/coins, a pomodoro, a countdown, a stretch reminder, GitHub CI and dev servers; switch one on in the Plugins page and give it a city or a repository, no terminal needed, and they start with her. They run inside her own process: no PowerShell, no process of their own. Any other is a script sending a few words to `127.0.0.1:47213/widget`, as [docs/WIDGETS.md](WIDGETS.md) says; a [Thunderbird extension](../integrations/thunderbird) sends the unread count from Thunderbird. A private widget such as mail shows only its count while Show the specifics is off. A plugin may open the island once to tell you something (before a meeting, say), but never while a session waits on you. The Plugins page of the settings turns them on and off, orders them, and sets how often they take turns. In the open capsule each plugin has a line: small, one line; medium, two (the second a few words more, the weather's range for the day), with a small curve where it has one. One with a large size (the weather, the system monitor, stocks, mail, Claude today) has a › at its right: a click unfolds its card in place, another folds it: the weather's next 24 hours as a curve, every second hour with its sky, tomorrow and the day after; the monitor's last minute of CPU, its memory, graphics card, drive, network and uptime (the graphics card and the drives read only while the pointer is on her home, never otherwise); a stock's day, high and low, volume and the plugin's others; mail's newest unread; Claude today's turns by the hour. What is not read says so. A right click on a plugin changes its size (small, medium, large; one it has not greyed, saying why under the pointer) and where it goes, the taskbar, the capsule or the desktop; each line of the Plugins page has the same choice. On the desktop (Windows) it lies over the wallpaper and under the windows, still there when Win+D shows the desktop: a pane of frosted glass over that display's wallpaper, blurred; it snaps to a 72 px grid, moves off the desktop's icons to the nearest free spot when dropped on them, and keeps its place on each display. On the pointer's, two buttons at its top right, Size and More; a double click opens its settings. Dragged onto another of the same size and held there half a second, the two stack; a drag moves the whole stack, the wheel or the dots at its right turn it, and its menu takes one out or takes it apart. A plugin is in one place: put on the desktop or the taskbar, it no longer takes turns in the closed capsule nor stays pinned at its right end (the monitor's readings, say); the capsule opened by a hover still lists them all, as an overview. Or into a board: a larger pane of the same glass with a title bar (its name, which a double click renames; Add, to pick from the widgets there are, into its first free cell; More; Fold, which leaves the title bar with its widgets' small icons); in it the widgets are flat tiles on the same grid, up to four rows: one dragged onto it lands in the nearest free cell, a full board gives a little shake, and one dragged out over its edge stands alone again; stacks don't go into a board. ### Updates

The downloaded exe looks at the latest release on GitHub and on Gitee as it starts (GitHub's `https://api.github.com/repos/zhoupengjie/Wakuwaku/releases/latest`; on Gitee, the repo's tags and the `.sha256` file in a release; with no account of yours), then once a day. Drafts and prereleases don't count. A new version is told on the island once; click it for Updates on the General page of the settings, where you can read its notes. Nothing is downloaded until you click Update.

- What's downloaded is the release's `wakuwaku-v<version>-windows-x64.exe`: from Gitee first in China, from GitHub first elsewhere, and from the other if that fails (Download from, under Updates, picks one). Looks and downloads go the way the General page's Network proxy says: Windows' proxy first (what Clash or v2rayN set when their system proxy is on), then straight, by default; a proxy typed in (HTTP or SOCKS5, its Test reaching GitHub through it); or straight. Crash reports, the plugins and the LibreHardwareMonitor download go the same way, and mail unless its page has its own. If a download times out with a VPN in TUN mode and only its local port open, pick Manual there and type it in (Clash's 7890, say). A failure says which way it went and at which address it stopped, and points to the Network proxy.
- It's checked against the SHA-256 GitHub gives for it, or, when GitHub gives none, the `.sha256` file in the Gitee release. If it doesn't match, none is given, or the two differ, it isn't installed and no file is touched.
- Once it checks out, your exe is renamed `<its name>.old.exe` and the new one put in its place (your file name kept); the new one starts, and the old one quits once the new one has said it is up and run on for a few seconds, after any prompt waiting for you is answered. Once the new one has run a minute, `.old.exe` is deleted.
- If an antivirus stops it (the exe is not signed, and some take a new version just downloaded and started for something suspicious, ending it or taking it away): the old one doesn't quit; it takes its own name back and runs on, and says on the island and under Updates that the update was stopped. Trust Wakuwaku (or its folder) in the antivirus and click Update again, or download it from the release page yourself. Taken away after it had started, the new one leaves only `<its name>.old.exe` in the folder: open it, and it takes its own name back.
- If the new one won't start and is still there: quit her, delete the new exe and rename `.old.exe` back to the name it had.
- To stop the checks: turn off Check for updates there, and click Check now when you want to.
- Run from source, she never checks or updates: building it again is the update.

### Crash reports

After she quits unexpectedly (a crash), the island asks you once, at her next start, whether to send crash reports automatically from now on. Click it to see everything that would be sent, then choose Send from now on or Don't send. You can switch it any time under Crash reports on the General page of the settings.

- A report is posted **publicly** as an issue: on Wakuwaku on Gitee in China, on GitHub elsewhere. One crash gets one issue; the same crash again only adds to its count.
- It holds her version, what crashed and where, Windows' and WebView2's versions, whether she lives in the island or the taskbar, how long she had run, and the last few minutes of her log.
- Taken out before it's sent: user and computer names, paths (as `%USERPROFILE%`), other programs' names (only Explorer and her own are kept), window titles and tray tips, mail addresses and accounts, session and project names, anything that looks like a token, and every word in Chinese or any other non-English script.
- There's no account or token in the exe: reports go to a relay (its code is in `relay/`), which opens the issue and limits how many one address can send.
- A report that can't be sent stays in `crashes/` in her data folder and is tried again later. Run from source, she only keeps them, and never asks or sends.

### Uninstall

1. If you turned on **Start at login**, turn it off on the General page (the `Wakuwaku` Run entry and the `Wakuwaku at logon-…` task both go).
2. With the plugin: in Claude Code, `/plugin uninstall wakuwaku@wakuwaku`, then `/plugin marketplace remove wakuwaku`. With hooks in settings.json: open Claude Code's row on the Agents page and click Remove; only this project's entries go, your own hooks stay, and the file as it was before the first change is at `~/.claude/settings.json.wakuwaku.bak`. With Codex: click Remove in its row's details; the backup is `~/.codex/hooks.json.wakuwaku.bak`. With OpenCode: click Remove in its row's details; it deletes `~/.config/opencode/plugins/wakuwaku.js`. With omp: click Remove in its row's details, which deletes `extensions/wakuwaku.ts`. With ZCode: the same in its row; the backup is `~/.zcode/cli/config.json.wakuwaku.bak`. With DeepSeek Harness: the same in its row; our lines leave `~/.dsh/cordis.patch.yml` (the file goes when nothing else is in it), the plugin leaves `~/.dsh/wakuwaku/`, and the file as it was, if there was one, is beside it as `.wakuwaku.bak`; with the official hook bridge, its two packages leave the profiles too.
3. Quit her, then delete the exe or the project folder. Notifications register her name in `HKCU\Software\Classes\AppUserModelId\com.zhoupengjie.wakuwaku`; delete that key too.
4. Delete her settings and downloaded pets: the `wakuwaku-data` folder beside the exe, or the project's `data/` when run from source.

> From source, remove the hooks before deleting the folder: they hold the program's path. If you moved the folder, settings will say the hooks point somewhere else; click Repair.

Each pet has 11 animations, and every one of them has a job:

| Animation | When | From which hook |
| --- | --- | --- |
| Idle | Nothing going on (a blink, then a few still seconds) | After you've seen an ending (mouse over her); `SessionEnd` |
| Running | Claude is working; the island shows how long this turn has taken | `UserPromptSubmit`, `PreToolUse`, `PostToolUse` |
| Waiting | Waiting on you: a permission prompt, a question, a plan to approve, an MCP form | `PermissionRequest`; `PreToolUse` (AskUserQuestion / ExitPlanMode); `Elicitation` |
| Review | The turn edited files and is done, ready for you to look | `Stop` (after Edit / Write and friends ran this turn) |
| Waving | The turn is done without edits; hello when a session starts or she appears | `Stop`, `SessionStart` |
| Jumping | A task on the to-do list is done; you clicked her | `TaskCompleted` |
| Failed | A request failed (stays until you've seen it); a tool call failed (a quick flash) | `StopFailure`; `PostToolUseFailure` |
| Run right / left | A short stroll when idle; running the way you drag her | — |
| Look around (16 directions) | Her eyes follow the mouse when idle; now and then she glances around | — |

- **Several Claude Code sessions at once**: each keeps its own state. She shows the one that most needs you (waiting > error > review > done > working) and tells you how many others are busy; when another one is waiting on you, the bubble's second line names it. Sessions left idle too long stop piling up: one at rest (a finished one from when you saw it) with nothing new for 30 minutes leaves the "+N", the open island and the settings' list of sessions, while its window's button stays on the taskbar; its next event brings it straight back, state, name and today's counts intact. - **Where it is, at a glance**: a session goes by its name in Claude Code (from `/rename` or the desktop app's title; else the first thing you asked). While it works she says the step it is on: "Editing island.rs", "$ cargo test", "Agent: explore the code", "Thinking", with "for 1:12" once a step runs long, and "3/7" and a progress bar when it keeps a to-do list. Waiting, she says on what ("Needs your OK: $ git push"); done, how many files changed and a line of Claude's reply; failed, why ("Usage limit reached"). The project is the git repository's name, worktrees included. When sharing your screen, turn off Show the specifics on the Look page and only the project and the status show.
- **Endings don't slip by**: done, review and error, a hello and a plugin's nudge too, stay 8 seconds by default: the island opened by itself stays open that long, and the ring stays lit and still that long after its two turns, then becomes a dot. - **Context compaction** also fires `SessionStart`; she ignores it and doesn't drop back to idle mid-work.

## Answer Claude on the pet

| What | What the panel lets you do |
| --- | --- |
| Permission ("Allow Bash to run npm test?") | **Allow** / **Always allow** / **Deny**, with the command and project shown |
| A question (AskUserQuestion) | Pick options, type your own answer, fill text and number questions; several questions and multi-select work |
| A plan (ExitPlanMode) | **Approve** / **Deny** |

- The terminal's own dialog still appears, and **whichever answer comes first wins**: answer on the pet and the terminal dialog closes; answer in the terminal and the panel goes away.
- **Always allow** adds the rules Claude Code itself suggests (the same as "don't ask again" in the terminal), and the panel spells out which rule goes where. It only ever adds allow rules.
- Buttons stay disabled for 0.6 s after a panel appears, so a click already on its way can't hit them. To type, click the box first; she takes the keyboard only then, never from the window you're typing in.
- How long the panel waits is up to you (30 s to 5 min); after that the terminal has it. In do-not-disturb, or while an app is full screen, prompts go straight to the terminal.
- Limits:
  - After you answer in the terminal, the panel closes on that session's next event, so it can linger for a moment. Clicking it then does nothing.
  - Non-interactive runs such as `claude -p` wait for the hook before deciding, so with nobody clicking they wait until the panel gives up.
  - MCP forms (Elicitation) are announced, not filled in.
- Codex's permission prompts come to the panel too, with **Allow** / **Deny** only (Codex takes no rules from a hook). Codex shows its own dialog only once the panel lets go, so the panel waits 1 minute at most; to answer in the terminal, click Handle in terminal.
- OpenCode's permission asks come to the panel too: **Allow** / **Always allow** / **Deny**. OpenCode asks in its own window at the same time, and the first answer counts; OpenCode keeps an "always" for that project.
- omp's (oh-my-pi's) plan reviews come to the panel too: **Approve** executes the plan, **Deny** has omp refine it; omp's own review stays open in the terminal meanwhile, and answering there first puts the panel away. omp's tool approvals she can't answer (omp gives an extension no way to), only remind you to go to the terminal.
- ZCode's permission prompts too, with **Allow** / **Deny** only; ZCode shows its own dialog at the same time, the first answer counts, and Handle in ZCode hands it back.
- DeepSeek Harness's approvals (its sandbox widened to danger-full-access for a write outside the workspace or a command, say) come to the panel with **Allow** / **Deny** (DSH only ever allows once: no "always"), DSH's own reason under them; when it asks you something with `ask_user_question`, pick an option (or several) or type an answer on the panel. DSH asks in its own window at the same time, and **the first answer counts**: answered on the panel, DSH's approval box (or question card) closes and it goes on; answered in DSH first, the panel goes. Handle in DeepSeek Harness hands it back.
- Reasonix's approvals are still answered in Reasonix for now: the island only shows what it is waiting for you to approve ("Approve in Reasonix: …").

## How it works

```
Claude Code ──HTTP hooks──▶ the pet (127.0.0.1:47213/hook)
            └─SessionStart─▶ the app itself --wakuwaku-ensure-running (in the background; starts her if she's not up)
Codex ──command hooks──▶ the app itself --wakuwaku-codex-hook ──▶ the pet (/hook?agent=codex)
OpenCode ──the plugin wakuwaku.js in its background service──▶ the pet (/hook?agent=opencode)
omp ──extension wakuwaku.ts (inside omp's process)──▶ the pet (/hook?agent=omp)
ZCode ──process hooks──▶ the app itself --wakuwaku-zcode-hook <event> ──▶ the pet (/hook?agent=zcode)
DeepSeek Harness ──plugin wakuwaku.js (inside DSH's process)──▶ the pet (/hook?agent=dsh)
Reasonix ──command hooks (cmd)──▶ the app itself --wakuwaku-reasonix-hook <event> ──▶ the pet (/hook?agent=reasonix)
```

- Every event is a Claude Code **HTTP hook** sent straight to her, so a tool call starts no process (about 0.3 ms here). She answers `{}` at once, meaning no decision; only a prompt waits until you answer on the panel.
- Claude Code runs no HTTP hook for `SessionStart`. The settings.json way gives it a background command instead: the app itself, which passes the event on if she's up (a hello) or starts her if not. No Node needed. The plugin has no such command; she starts at login.
- At rest she takes about 1% of one core (measured on Windows 11) and about 185 MB of private memory, mostly WebView2 (that is, Chromium) itself.

| Variable | Does |
| --- | --- |
| `WAKUWAKU_PORT` | Another port (default 47213); set it for both her and the hooks |
| `CLAUDE_CONFIG_DIR` | Claude Code's config folder, when it isn't `~/.claude` |
| `CODEX_HOME` | Codex's config folder, when it isn't `~/.codex` |
| `REASONIX_HOME` | Reasonix's home, when it isn't `%APPDATA%\reasonix` (found as Reasonix finds it) |
| `OPENCODE_CONFIG_DIR`, `XDG_CONFIG_HOME` | OpenCode's config folder, when it isn't `~/.config/opencode` (found as OpenCode finds it) |
